# Character Continuity v2.02-test-b3 notes

This test release changes how Character Continuity reaches the model and how operation families are scheduled. It does not change the creator-owned source-card formats.

## What changed

- CC creates one generated `CC — Model Context — Name` Story Card for each activated NPC.
- That card normally uses the canonical name and unambiguous Active aliases as native triggers; a currently mentioned managed alias can be added transiently so Emerging, Retired, or Rejected status remains available when needed.
- Its Entry is a bounded portrayal projection: compact Outer and Inner, then complete optional blocks that fit for current State, Turning Point stage, Relationships, Views, Names, and one Experience.
- Source and storage cards retain internal keys and do not become ordinary scene-triggered lore.
- Front Memory contains only a current task, a prose-recovery task, or an unpromoted possible-next task staged for Continue.
- Ordinary no-task turns contain no CC Front Memory block.
- CC owns only the text between `<CC_FRONT_MEMORY>` and `</CC_FRONT_MEMORY>` and preserves surrounding Front Memory.
- Input prepares and stages an Input/Retry task before platform context assembly. After a completed Output, CC separately pre-stages a possible Continue task without replacing the completed plan.
- In enabled task verification, Context does not construct, append, replace, or resize the task. It marks a task delivered only after the incoming context ends with the exact complete `state.memory.frontMemory` value already staged for that plan. Disabled-mode cleanup may remove CC's owned block.
- Context Viewer refreshes do not promote the pending Continue plan. A genuine newer action count does.
- Each staged task carries a preparation fingerprint. A source-card, settings, evidence, or managed-state change before Context invalidates it, clears the queued plan and owned Front Memory state, and authorizes no operation. Context cannot remove the stale copy from text the platform already assembled, so it still returns that incoming text unchanged and Output rejects or strips its CCO record.
- Each response can authorize at most one operation family for one fixed active NPC. The scheduler freezes Name, State, Relationship, View, or Turning Point before prompt construction using lowest owner/family drain followed by fairness and relevance tie-breaks. The model still decides whether the supplied evidence supports a change within that family or `K`.
- Drain is now stored per owner/family instead of per evidence/target/signature. A completed operation or unchanged assessment drains only that family, while later opportunities for the same owner decay it and favor other ready families.
- The operation-task payload ceiling is 600 estimated tokens; the ownership tags are budgeted separately. Normal tasks fit within 592 tokens, reserving eight for the Retry label. Assessment projection remains bounded to two evidence rows, five targets, and up to three Turning Point choices. `K` closes only the scheduled family's complete shown scope; omitted legal scope remains reviewable. A generated Model Context card targets at most 1,000 characters for attention and has an absolute 2,000-character Story Card ceiling; optional material is added only as complete blocks.
- A Retry that reruns the Input hook is fully rebuilt and restaged. A Context-only retry of an AI Continue cannot choose safely between the prior and possible-next tasks after platform assembly, so this cache-compatible build makes that response prose-only and authorizes no continuity operation.

## Safe test procedure

1. Duplicate the Scenario or preserve the four installed v2.01 script tabs.
2. Replace Library, Input, Context, and Output with the four files in this package.
3. Keep `// @cache-compatible` as the first Context line.
4. Start a fresh Adventure for the cleanest comparison.
5. Enter an action that mentions one activated NPC by canonical name.
6. Confirm that exactly one `CC — Model Context — Name` card exists and its keys include the name.
7. Open the Context Viewer. The generated card should appear when its name triggers; CC should not append a second full portrayal packet at the end.
8. Before Context, staging reports `Front Memory: prepared-operation | verified No`. After an assessment Context pass, check `CC — Status` for `Front Memory: operation | verified Yes`, exactly one scheduled family, and a task payload at or below 600 tokens.
9. After Output, expect `Front Memory: prepared-operation | verified No` when CC has staged a possible Continue task. A following Input replaces only CC's tagged block; unrelated Front Memory text remains byte-for-byte intact.
10. Confirm that no `(CCO|...)`, `<CC_FRONT_MEMORY>`, or `<SYSTEM>` control text appears in visible story.

## What to report from a failed case

Enable `Debug: true` for one action and preserve:

- the complete generated output before manual editing;
- `CC — Status`;
- all `CC — Debug` pages;
- the affected NPC's generated Model Context card;
- whether the action was Input, Continue, Retry, or Context Viewer refresh; and
- whether another script also edits Context or Front Memory.

If the pre-staged Front Memory task cannot be verified, check that another script has not placed text after the current `state.memory.frontMemory` value or changed CC's tagged block between Input/Output and Context.

## Rollback

Restore the four v2.01 script tabs, then remove only the generated cards whose keys begin `__CC_MODEL_CARD__:`. v2.01 does not maintain them, but their name triggers would otherwise remain active. Do not remove creator source cards or managed State, Names, Relationships, Views, Turning Points, or Experiences cards.

## Included automated check

Run from the package directory:

```sh
node tests/hybrid-memory.test.js
node tests/blocker-one-liveness.test.js
node tests/assessment-family-fit.test.js
node tests/retry-lifecycle.test.js
```

The checks exercise generated triggering, Active-versus-Rejected alias keys, the card-size bound, exact preservation of unrelated Front Memory, Input and Output pre-staging, byte-for-byte enabled-mode Context verification, Context Viewer/Continue separation, duplicate prevention, delivery despite a crowded already-assembled context, frozen-evidence carry, prose recovery, hidden-record stripping, disabled-mode cleanup, and safe refusal when Front Memory is not the actual suffix. The stress fixtures cover two maximum evidence excerpts, five legal targets, all five scheduled-family forms, the five-active-NPC limit, family-scoped `K`, owner/family drain rotation, cross-family rejection, Retry headroom, and the 600-token ceiling.
